# Video Wallpaper v0.8 release plan

In v0.8, users should be able to paste a YouTube link, choose a segment, and use it as wallpaper on the TV. Improve download reliability first, then add a trim preview that works with the TV remote and test optional 1080p. The quick-download default is the first two minutes, 720p, with audio on. Downloaded clips stay in the app’s private wallpaper library.

## Implementation tasks

### 1. Diagnose failed and slow source lookups · Release blocker

- [ ] Reproduce with the screenshot’s video ID and a known-compatible prerecorded clip. For the Fire TV report, request the exact link, full error, app version, Fire OS version, and whether audio was on. Track lookup, copying, and saving times separately.
- [ ] Use extractor metadata to distinguish active or upcoming live streams from completed replays. Explain unavailable formats, missing audio, access restrictions, and connection failures separately when the evidence supports that distinction. Preserve existing access checks and keep signed media URLs out of diagnostics.
- [ ] Keep progress visible during lookup and copying. Add a way to cancel and retry without leaving partial clips in the library or discarding the active selection. Reuse a still-valid resolution result if a preview led to a download, so playback setup does not repeat the slow lookup.

**Done when** a compatible prerecorded link works, an active or upcoming stream gets a specific message, a compatible replay passes the normal eligibility checks, and a failed or cancelled attempt leaves existing wallpapers intact.

### 2. Base clip size on available storage · Release blocker

- [ ] Replace the fixed 32 MiB-per-minute budget with a free-space check that accounts for temporary output and leaves room for TV operation. Keep the five-minute maximum on the saved segment. Preserve source quality and remove partial files if the TV runs out of room.
- [ ] Use available bitrate or size metadata to estimate selected-segment size before copying. If no reliable estimate exists, track the output during copying and handle actual write failures cleanly. Show a storage-specific message with a next step, such as freeing space or choosing a shorter clip.
- [ ] Test a source longer than five minutes and a trimmed result above 64 MiB. Separate storage failures from duration or format failures in the UI.

**Done when** the high-bitrate two-minute fixture that failed on v0.7 saves with sufficient space, and a low-storage run fails cleanly without changing the library.

### 3. Add start and end controls with a preview · Core feature

- [ ] Prototype a **Trim** dialog with a large preview, a timeline with start and end markers, and labeled timestamps. Make both markers adjustable with the TV remote and allow direct `mm:ss` entry for long videos. Keep the existing one-click download flow available with default settings.
- [ ] Load source metadata before enabling the timeline. Preview the selected segment and clamp its end to the source duration. Support a segment under five minutes anywhere in an eligible video, with audio and video aligned.
- [ ] Verify actual trim boundaries on long-GOP video. If lossless cuts need to align to keyframes, show the actual boundaries in the editor. Evaluate frame-accurate trimming separately if it requires slow or quality-reducing re-encoding on a TV.
- [ ] Store the trim range with each saved entry so the same URL can produce different clips. Migrate old entries as starting at `0:00`, preserving files and selections.

**Done when** a remote user can pick and preview `1:30` to `3:30` from a seven-minute source, then save that segment as a separate clip. Preview and saved boundaries agree within the published tolerance, and audio stays in sync.

### 4. Simplify the main screen · Core feature

- [ ] Move **Add MP4 file** into **More**. Keep existing imported clips playable and selectable after upgrade.
- [ ] Verify that deleting a clip removes its private library file and updates the list shown to Projectivy.

**Done when** the remote can open **More**, import a compatible clip, and manage previously saved wallpapers.

### 5. Clarify TV setup and respond to feedback · Core feature

- [ ] Add short setup help in the app and README. Install the plugin on the TV, add or download a clip on the TV, then select the provider in **Projectivy Settings → Appearance → Wallpaper → Launcher wallpaper**. Explain the Premium requirement and the private library.
- [ ] On a phone, explain that selecting a wallpaper affects that device’s library and that the TV setup happens on the TV. Keep phone-to-TV transfer and remote control outside v0.8.
- [ ] Prepare replies for review. Ask for the source link and full error for the Fire TV and access reports. Explain the TV setup to the phone user. Acknowledge that direct MP4 import already works for people with a file ready. Thank the TCL reporter and describe 1080p as under device testing.

**Done when** someone with the APK and Projectivy Premium can follow the instructions on a TV from installation to a playing wallpaper without extra help.

### 6. Add optional 1080p · Hardware test gate

- [ ] Offer **720p** and **1080p**. Keep 720p as the default and show the actual saved resolution. If compatible 1080p H.264 is unavailable, offer a clear 720p choice. Keep the original video quality when copying either resolution.
- [ ] Include resolution in the saved options and clip identity. Migrate v0.7 YouTube entries as 720p and preserve existing local imports at their actual resolution.
- [ ] Check playback, audio, looping, file size, and preparation time on physical TVs. Ship 1080p only with a passing hardware check. Defer 4K until the supported devices and formats are measured.

**Done when** a supported 1080p YouTube clip plays as a Projectivy wallpaper on physical test hardware and an unavailable 1080p stream produces the 720p choice with an accurate label.

## Build and release sequence

1. **Fix the download path.** Complete tasks 1 and 2 first. Run the long-source, large-output, cancellation, and low-storage cases before starting UI work on the trim dialog.
2. **Build the TV workflow.** Implement the trim editor and setup help. Verify remote focus, readable timestamps, and returning from the editor or system picker. Add 1080p once the clip and storage paths pass.
3. **Test a release candidate.** Run unit tests, lint, and APK assembly. Use synthetic clips with visible time markers and a tone for boundary and audio checks. Test an in-place upgrade from v0.7 with multiple selected wallpapers and an existing local import. Verify selection, rotation in Projectivy, restart, and disk deletion. Use the Philips and Rockchip devices for physical checks. Seek a Fire TV retest and a TCL 1080p retest from the reporters if those devices are unavailable locally.
4. **Publish after verification.** Update the README and real TV screenshots, record the hardware tested, and verify the existing signing certificate and APK checksum. Merge the tested branch and publish the signed v0.8 APK and checksum with release notes after approval. If 1080p misses its hardware gate, release the verified fixes and trim workflow first.
